# Round 6: priority guide, program swaps, picker filters, folding, sharing, cycle phase

## Owner decisions (2026-10-13)

- Priorities: **a guide and a warning**, not a cap. Ranges shifting when a priority moves is expected and stays as is.
- Program builder: a **Swap** button on every lift, with suggested alternatives.
- Exercise picker: **filter by muscle**, main muscle by default, with a toggle that also counts secondary muscles.
- Today: **any card can fold**, not only finished ones.
- Sharing: a **gym** (its equipment), three ways: add from a friend's view, send to a friend, or copy as text. No history.
- Cycle phase: an opt-in setting. **Hand-entered on gym days, one tap under Energy.** Once there's enough data, the predicted phase gets a subtle highlight. **Never visible to friends.**
- The pets and points game (mascots, upgrades, clothes, food, points) is the next round, with its own design questions.

Order of work: A → B → C → D → E. Each part ships on its own.

## B. Swap in the program builder

- Every slot in `ProgramScreen` gets a **Swap** button. Each row then has Swap, −, sets, +, ×; check that it fits at 375 px.
- Swap opens `ExercisePicker`:
  - `title`: "Swap Bench Press".
  - `suggested`: `swapSuggestions(slot.exercise, entries, today, 5, availableSet(gym, …))`, the same scoring Today's Swap uses (similar muscles, gear this gym has, recent pain).
  - `gym`: the active gym.
- Picking a lift replaces the slot in place. It keeps the set count and takes its rep range from `defaultSettings(name)`. If the day already has that lift, its sets are added to the existing slot instead. The swap goes through `edit()`, so the program is marked as edited.
- **Deprioritised in rebuilds, not banned** (owner, 2026-10-14). `Profile.avoid?: string[]`. Swapping a lift out adds it to `avoid`, and `candidates()` in `domain/program.ts` sorts avoided lifts after every other candidate for that muscle. They are still used when nothing else trains the muscle. A "Picked last" line under the program lists them, each with a ✕ to clear it. `avoid` syncs through `meta/profile` like the rest of the profile.
- **Tests.**
  - Unit: `buildProgram` picks an alternative over an avoided lift, and still picks the avoided lift when it's the only one for that muscle.
  - e2e: Swap → pick a suggestion → the slot is renamed with the same sets, the old lift is listed under "Picked last", and a rebuild uses the alternative.

## C. Muscle filter in the exercise picker

- A row of muscle chips under the search box. One muscle at a time; tapping it again clears the filter. Every picker gets this (Today add, program add, swap).
- A "+ secondary" toggle chip. When it's off, only lifts where that muscle has weight 1 in `muscleVector` match. When it's on, any weight above 0 matches.
- The filter combines with search text.
- Lifts with no known muscles are hidden while a filter is on. A muted line says how many: "3 lifts with unknown muscles hidden".
- Matching happens in `domain/muscles.ts`: `trains(name, muscle, secondary): boolean`.
- **Tests.**
  - Unit: `trains('Bench Press','Triceps',false)` is false and with `true` it's true; `trains('Cable Pushdown','Triceps',false)` is true; an unknown name is false.
  - e2e: picking Triceps lists Cable Pushdown but not Bench Press; "+ secondary" adds Bench Press.

## E. Share a gym

Owner decision (2026-10-14): share a **gym**, meaning the equipment set-up the program builder asks for. That's not the program and not history. It can be shared three ways.

**1. Add from a friend's view.**
- A friend can already read your `meta/profile`, and that includes `gyms`.
- FriendView gets a "Gyms" list, and each gym on it has an **Add to my gyms** button.
- Adding copies the gym with a fresh id. If the name is already taken, " (2)" is added to it.
- No rules change is needed.

**2. Send gym to a friend.**
- Gyms screen → a gym → **Send to…** → pick a friend.
- This writes `users/{friend}/gymInbox/{autoId}` = `{ from, fromName, gym, sent }`.
- The friend sees "Pat sent you a gym: Downtown Fitness", with **Add** and **Dismiss**, in the same place friend requests show. Either button deletes the inbox doc.
- Rules:
  ```
  match /gymInbox/{id} {
    allow create: if signedIn() && request.resource.data.from == request.auth.uid
                  && exists(/databases/$(db)/documents/users/$(uid)/friends/$(request.auth.uid))
                  && request.resource.data.keys().hasOnly(['from','fromName','gym','sent']);
    allow read, delete: if me(uid);
  }
  ```

**3. Copy as text** (for people who aren't friends in the app).
- Gyms screen → a gym → **Copy as text**. If the clipboard is refused, it shows the block in a selectable `<textarea>` instead.
  ```
  Gym Tracker gym: Downtown Fitness
  Equipment: barbell, squat rack, plates, dumbbells, cable stack, leg press
  Not here: Hip Thrust
  Also here: Belt Squat
  ```
- Gyms screen → **Add from text**. Paste a block, see a preview, then Save.
  - Equipment names that aren't in `EQUIPMENT` are skipped, with a note listing them.
  - Text with no header shows: "This doesn't look like a copied gym."

**Code.** `domain/share.ts` holds:
- `gymText(g)`
- `parseGymText(s)`
- `copyGym(g, existing)` (fresh id, unique name)

All three ways go through `copyGym`.

**Tests.**
- Unit:
  - the text round trip keeps name, equipment, exclude and include;
  - unknown equipment is reported;
  - text without the header gives an error;
  - spaces and case are tolerated;
  - `copyGym` makes a unique name and a new id.
- Rules (emulator):
  - a friend can create an inbox doc;
  - a stranger can't;
  - a friend can't forge `from`;
  - only the owner can read or delete;
  - a mutation that drops the friend check must fail a test.
- e2e:
  - adding a gym from a friend's view;
  - sending a gym, then accepting it on the other account;
  - Copy as text → Add from text gives the same equipment ticked.

## F. Cycle phase (opt-in)

**Model.**
- `CyclePhase = 'period' | 'follicular' | 'ovulation' | 'luteal'`.
- `CycleDay { date; phase }` lives in its own IndexedDB store (`cycle`). It's per profile, like body days, but stored apart from them.
- Setting: `cycleTracking: boolean` (default off). It's turned on from the Data tab.

**Input.** When the setting is on, a chip row "Cycle" sits under Energy on Today, with Period · Follicular · Ovulation · Luteal. One tap saves the phase, and tapping the chosen chip again clears it. It's the same pattern and size as Energy.

**Prediction** (`domain/cycle.ts`, pure):
- A cycle starts on a logged `period` day that has no `period` day in the 10 days before it.
- A cycle's length is the gap between two consecutive starts, counted only if it falls between 21 and 45 days. A missed log can make a gap look like two cycles, and those are dropped.
- Enough data means at least 2 counted lengths. The length is their median.
- On cycle day `n`, counted from the last start, with length `L`:
  - day 1–5 (`n ≤ 5`) is `period`;
  - from day 6 up to 3 days before ovulation's midpoint (`n < L − 16`) is `follicular`;
  - days `L − 16` to `L − 12` are `ovulation`;
  - after that is `luteal`.
  - This uses the textbook luteal phase of about 14 days, which varies less than the follicular phase does.
- No prediction is made if `n > L + 10` (a late or missed start), when the setting is off, or without enough data.
- **Display.** The predicted chip gets a faint dashed outline (`.chip.predicted`), with no fill and no label. It is not pressed and nothing is saved until it's tapped.

**Privacy.**
- Cycle days never go in `BodyDay`, the `months` docs or `meta`, because friends can read all of those.
- They sync to `users/{uid}/private/cycle`, one doc `{ days: Record<date, phase>, tracking: boolean, updatedAt }`, merged per date with the phone winning.
- Rules: `match /private/{d} { allow read, write: if me(uid); }`.
- Friend view never reads `private`.
- They are excluded from the body CSV export.
- Turning the setting off hides the UI and keeps the data. "Delete cycle data" (with a confirm) clears the store and the cloud doc.

**Tests.**
- Rules (emulator):
  - The owner can read and write `private/cycle`.
  - A friend cannot read it.
  - A stranger cannot read it.
  - A mutation that adds `|| friendOf(uid)` must fail this test.
- Unit:
  - starts detected with a gap of 10 or more days;
  - gaps outside 21–45 are dropped;
  - no prediction with fewer than 2 lengths;
  - the phase boundaries for L = 28 (day 5 is period, day 6 follicular, day 12 ovulation, day 17 luteal);
  - no prediction past L + 10.
- e2e:
  - with the setting off, there's no Cycle row;
  - with it on, a tap saves and survives a reload;
  - with seeded synthetic history, the predicted chip has `.predicted` and isn't pressed;
  - a friend's view shows no cycle data.
- Synthetic fixtures only.

**Deploy.** The rules change goes out with `firebase deploy --only firestore:rules` before the app build that writes `private/cycle`. Until it's deployed, those writes are refused, and the app logs and carries on.
